# [Bug] agent-leak-app이 CPU 부하 임계치 위반을 기록한 직후 종료됨

## 현상과 비교 결과

2026-11-20에 동일한 Linux 이미지에서 `CPU_MAX_OCCUPY`만 바꿔 두 번 실행했다. 아래 Before는 장애 설정, After는 완화 설정이다. 실제 수집 순서는 10%, 100%였으며 시각은 UTC다.

| 지표 | Before · 100% (run-100) | After · 10% (run-10) |
| --- | --- | --- |
| 대상 PID | 23 | 22 |
| 앱 내부 부하 | 5.00%에서 58.71%까지 상승 | 10.00% 도달 후 부하를 낮추는 주기 반복 |
| OS에서 측정한 앱 PID의 최대 CPU 사용률 | 57.0% (기동 중), CpuWorker 시작 후 11.9% | 99.0% |
| 서비스 수명 | 포트 수신 시작부터 종료 회수까지 32.833초 | 포트 수신 후 82초 이상 생존 확인 |
| 종료 관찰 | 임계치 위반 직후 상태 143 | 90초 제한을 둔 실험에서 상태 137로 회수. CPU 정책 종료 로그 없음 |

100% 실행은 09:01:44.959에 포트 수신을 시작했고 09:02:17.792에 수집기가 종료를 회수했다. 10% 실행은 08:59:53.456에 포트 수신을 시작했고 09:01:16에도 `top`에서 PID 22가 살아 있었다. 수집기는 `timeout -k 3 90`으로 실험 시간을 제한했다. 10% 실행의 코드 137만으로 종료 신호 발신자를 확정할 수 없어 생존 시간은 확인된 하한으로 제시한다. ## PID별 CPU 급상승 구간

10% 실행의 `top` 연속 표본에서 PID 22가 2초 사이에 코어 하나분의 CPU를 거의 모두 사용했다. 같은 시각 Linux 전체 CPU의 유휴 비율은 79.1%였다. `top`의 PID별 100%는 논리 CPU 한 개 분량이며 전체 요약은 여러 CPU에 걸친 평균이다. [원본 top 캡처](../evidence/cpu/run-10/top.log)

| 시각 | PID 22의 %CPU | PID 22의 누적 CPU 시간 |
| --- | ---: | ---: |
| 09:01:10 | 0.0 | 31.23초 |
| 09:01:11 | 42.0 | 31.65초 |
| 09:01:12 | 99.0 | 32.65초 |
| 09:01:13 | 6.9 | 32.72초 |

09:01:12에 앱은 내부 부하 9.50%와 힙 300MB를 기록했다. 이 실행에서는 같은 프로세스에 MemoryWorker도 동작했다. PID 전체의 CPU 사용량에는 이 작업의 비용도 포함되므로 99.0%를 CpuWorker 단독 사용량으로 돌릴 수 없다. [10% 앱 로그](../evidence/cpu/run-10/agent_app.log)

## 종료 근거

100% 실행의 마지막 세 줄이다. 앱이 내부 부하 58.71%에서 CPU 정책 위반을 명시했고, 38ms 후 수집기가 상태 143을 기록했다. 이는 일반적인 SIGTERM 종료 상태(128 + 15)와 일치하며 90초 실험 제한보다 앞선다. cgroup의 OOM 강제 종료 횟수도 실행 전후 0이었다. 증거는 앱의 CPU 보호 정책에 따른 종료를 지지한다. 실제 로그에 기록된 구성요소 이름은 `CpuWorker`이며, 별도 Watchdog 프로세스의 존재나 신호 발신 PID까지는 확인되지 않았다. [앱 로그](../evidence/cpu/run-100/agent_app.log) · [종료 상태](../evidence/cpu/run-100/exit.txt) · [회수 시각](../evidence/cpu/run-100/end.utc)

```text
2026-11-20 09:02:14,229 [INFO] [CpuWorker] Current Load: 49.42%
2026-11-20 09:02:17,640 [INFO] [CpuWorker] Current Load: 58.71%
2026-11-20 09:02:17,754 [CRITICAL] [CpuWorker] CPU Threshold Violated! (58.709999999999994%).
```

같은 실행에서 PID 23의 마지막 `top` 표본은 0.0%였다. 내부 부하가 상승한 구간에 OS의 구간 사용률이 함께 58.71%까지 올랐다는 근거는 없다. 100% 설정에서도 앱은 그보다 낮은 부하에서 보호 정책을 발동했다. 반면 10% 설정에서는 내부 부하가 설정값에 도달하자 `Peak reached (10.00%). Starting cooldown...`을 기록하고 계속 실행됐다. 이 바이너리에서 설정 변경은 워커의 부하 패턴에도 영향을 주며, 동일한 부하에서 종료 기준만 바꾼 실험으로 해석하기는 어렵다. [100% top 캡처](../evidence/cpu/run-100/top.log) · [10% 앱 로그](../evidence/cpu/run-10/agent_app.log)

## CPU 경쟁이 지연을 만드는 원리

실행할 준비가 된 요청 처리 스레드와 CPU를 많이 쓰는 워커가 같은 CPU 시간을 필요로 하면, 스케줄러가 워커를 실행하는 동안 요청 처리 스레드는 실행 큐에서 기다릴 수 있다. 이 대기 시간이 요청의 응답 시간에 더해진다. 실험 컨테이너는 CPU 시간을 1코어 분량으로 제한했으므로 할당량을 소진하면 같은 컨테이너의 다른 작업도 다음 할당 주기까지 지연될 수 있다. 이번 측정으로 확인한 것은 특정 PID의 순간 점유와 앱의 정책 종료다. 요청 왕복 시간이나 실행 큐 대기 시간은 측정하지 않았다.

## 재현 조건

Ubuntu 24.04.5 x86_64, UID 10001, CPU 할당량 1코어, 메모리 한도 1GiB에서 실행했다. 두 실행 모두 `MEMORY_LIMIT=512`, `MULTI_THREAD_ENABLE=false`로 고정하고 외부 요청 없이 관찰했다. `top -b -d 1` 원본에는 PID별 구간 사용률과 Linux 전체 요약이 함께 남는다. [재현 명령](../readme.md) · [수집 스크립트](../scripts/monitor-cpu.sh)
